# Phone gateway

Decision: workspace RFC-006. The backend side is `soloone-backend/docs/features/phone-gateway-transport.md` (WA-PGW-*).

## Contracts

- PGW-1: `POST /v1/messages` requires the bearer `GATEWAY_TOKEN`. The body has `messageId`, `from` (sender WhatsApp number), `to` (recipient phone) and either `text` with optional `typingTimeMs`, or `media` with `type`, `url`, `fileName`, `mimeType`, `caption`, `viewOnce`, `voice`.
- PGW-2: The response is `200 {outcome: "sent"}`, `422 {outcome: "failed", retryable, error}` when Send was not pressed, `502 {outcome: "unknown", error}` when Send was pressed but the sent bubble was not confirmed, or `409 {outcome: "in_progress"}` while the same message ID is running.
- PGW-3: Each message ID is recorded on disk before Send is pressed. A repeated request returns the recorded `sent` or `unknown` outcome and never presses Send again. Only `failed` attempts, and attempts interrupted before Send, may run again.
- PGW-4: The device is chosen by `from` from the device registry. A device driver only returns a working ADB serial. The `multilogin` driver starts a stopped phone and enables ADB through the Multilogin REST API, or through a logged-in `xcli` on the same host when no automation token is set. The `physical` driver connects to a fixed ADB address. Operations on one device run one at a time.
- PGW-5: Operations are declarative step scripts in `scripts/`. Resource ids from WhatsApp Business (`com.whatsapp.w4b:id/`) are read as `com.whatsapp:id/`, so one script serves both apps; the package to launch comes from the device registry. Guarded steps are code primitives: `open_chat`, `share_media`, `clear_input`, `type_text`, `type_caption`, `ensure_view_once`, `check_recipient`, `send`, `confirm_sent`, `find_message`, `open_reactions`, `choose_reaction`, `confirm_reaction`, `delete_for_everyone`, `confirm_deleted`, `open_edit` and `confirm_edited`. Free steps are `tap`, `dismiss_if_present`, `wait` and `back`.
- PGW-6: When a step does not find its element before Send, the recovery model gets the compact UI tree, a screenshot and the step goal, and returns one action: tap a listed clickable node, back, wait or abort. The gateway refuses taps on send, voice-note, call, camera, chat-list rows and destructive or share-confirm buttons. Recovery never runs after Send was pressed.
- PGW-7: After a run that needed recovery or failed on a missing element, the fixer model proposes a full script. A proposal is stored only when it keeps every guarded step in the same order and uses known step types. A proposal never becomes active by itself. A person can dry-run it (it stops before Send and clears the draft) and approve or reject it through the API.
- PGW-8: Text is typed as one piece; only when the request carries `typingTimeMs` is it spread over that time in small pieces. Non-ASCII text needs ADB Keyboard; without it the request fails before typing. The input is cleared first and the typed text is checked before Send. ADB Keyboard stays in place through Send, so no on-screen keyboard slides in under the Send button, and while the chat is held for the next part (PGW-37) the next part types without switching again; the phone's own keyboard is restored when the run leaves the chat.
- PGW-9: View Once is turned on or off to match the request and checked before Send. An opened View Once bubble shows `Seen` instead of `Read`, and it confirms the send the same way. A media send needs exactly one selected recipient. Text is sent only in the chat opened for `to`.
- PGW-10: Documents are rejected as not retryable without touching the phone. Photos and videos are supported; a photo is converted to JPEG and a video to MP4 before it reaches the phone. A voice note or audio file is sent as an audio file, not as a voice note (PGW-32).
- PGW-12: `POST /v1/reactions` takes `reactionId`, `from`, `to`, `emoji` (empty to remove `previousEmoji`) and a `target` with `text` or `mediaType` plus `sentAt`. The phone finds the newest matching bubble, preferring the one whose time label matches `sentAt` in the phone's time zone, and scrolls up a few screens when needed. Several matches without a time match fail without reacting. The emoji is looked up in the reaction tray, then the full picker, then the picker search by a keyword from the script. The tap is recorded like Send, and the reaction chip under the bubble is checked afterwards.
- PGW-13: After Send, a media bubble in `Pending` state extends the confirmation wait to the request deadline, and a `Retry` bubble is tapped once before the wait continues. A still unconfirmed upload is reported as `unknown`, never `failed`, because WhatsApp may still send it. The phone is woken right before the share opens and right before Send is tapped, and again whenever no screen is in front during the wait, because preparing a video can outlast the screen timeout of a phone on battery.
- PGW-14: `npm run selftest -- --from <test number> --to <recipient> [--react-text <text>]` runs the text, View Once photo with caption, View Once video and reaction-tray flows on that phone in dry-run mode. Nothing is sent: text drafts are cleared, media composers are closed, the reaction tray is closed before an emoji is chosen. The report names the failing script step and is written to `state/selftest/<date>.json` and `latest.json`; the exit code is 1 on any failure. The reaction check runs only when `--react-text` names a message already in that chat. A cloud test phone is stopped at the end of the run.
- PGW-15: A UI snapshot is reused for up to `UI_SNAPSHOT_CACHE_MS` (default 5 s) while nothing was done on the phone; every tap, key, intent and typing clears it, and the checks after typing, before confirming and after Send always read fresh. On the phones in `FAST_UI_SERIALS` the read is fast enough to catch the keyboard still sliding in after typing, so Send is located again until its position holds between two reads. Media download and conversion start before the phone connection and overlap with it.
- PGW-16: `open_chat` retries the deep link up to three times when WhatsApp answers the number lookup with its "Couldn't connect" dialog, pressing its OK in between.
- PGW-17: When an ADB command fails because the TCP link dropped (`device offline`, `not found`, connection reset), the gateway reconnects to that serial once and retries the command. A second failure is reported as usual. When a command times out (the link still lists as connected but hangs, as after the phone slept and the VPN reconnected), the gateway also reconnects that serial, but reports the failure without running the command again, because it may already have acted on the phone.
- PGW-18: Every 5 minutes the gateway checks each physical phone over ADB. After two misses in a row it e-mails `ALERT_EMAIL` once (subject "Phone +<number> is offline", with a ready message for the phone holder), and e-mails again when the phone answers. Cloud phones are not checked: they are stopped until needed.
- PGW-19: When a step's element is missing and a system UI tip window (`com.android.systemui:id/...tip...`) is on screen, the gateway presses Back once and reads the screen again before any recovery model is asked.
- PGW-20: Every failed or uncertain message or reaction leaves a report in `state/failures/<time>_<messageId>/`: the request, the error, each step with its note and start time (a typed-text mismatch notes what the input read back), and the screen at the moment of failure (activity, UI tree, screenshot). Reports older than 14 days are deleted. Screenshots show the phone's chats, so the folder stays on the server.
- PGW-21: `POST /v1/deletions` takes `deletionId`, `from`, `to` and a `target` with `text` or `mediaType` plus `sentAt`, and deletes that message for everyone. Only our own messages are considered: a bubble counts as ours when its row carries a delivery status icon. The bubble is found as in PGW-12 (newest match, time label preferred, a few screens of scrolling; several matches without a time match fail without touching anything). The gateway long-presses it, taps Delete and then only "Delete for everyone". When that button is missing (the message is too old, or not ours) it presses Cancel and fails as not retryable; it never taps "Delete for me". The tap on "Delete for everyone" is recorded like Send (PGW-3), and afterwards the chat must show "You deleted this message" in place of the bubble, otherwise the outcome is `unknown`. Responses follow PGW-2 and failures leave a report as in PGW-20. The backend and client do not call this endpoint yet.
- PGW-22: `POST /v1/edits` takes `editId`, `from`, `to`, the new `text` with optional `typingTimeMs`, and a `target` with the old `text` plus `sentAt`. It changes one of our own text messages; the new text must differ from the old one. The bubble is found as in PGW-21. The gateway long-presses it, opens More options and taps Edit; WhatsApp offers Edit only within 15 minutes of sending, so without it the menu is closed and the request fails as not retryable. The edit input is cleared, the new text is typed and checked as in PGW-8, and the save tap is recorded like Send (PGW-3). Afterwards the edit screen must be closed and our bubble must show the new text, otherwise the outcome is `unknown`. A dry run stops before saving, clears the input and leaves the edit screen. Responses follow PGW-2 and failures leave a report as in PGW-20. The backend and client do not call this endpoint yet.
- PGW-23 (RFC-012 phase 1): For each physical phone, unless the registry sets `captureIncoming: false` for it, the gateway reads the WhatsApp message notifications over ADB when PGW-42 signals one, every 5 seconds as a fallback and right before every operation that opens a chat, under the same one-at-a-time device lock. The output is filtered on the phone to the WhatsApp notification records. Each message in a one-to-one chat notification becomes an incoming record with the chat identity from the notification shortcut (`<lid>@lid` or the phone address), the sender name, the text and the time. Group conversations are skipped. A reaction notification ("Reacted 👍 to …") is recorded as a reaction and never reported as a message. A record is new when no earlier record has the same chat, time and text.
- PGW-24: A message whose notification text marks a photo, video, voice message or document is tied to the oldest unused file of that type in the WhatsApp media folder whose modification time is between 5 seconds before and 2 minutes after the message time. The file is copied off the phone into `state/incoming/media/`. A message with no such file within 2 minutes is recorded without media and the miss is noted.
- PGW-25: When a text send opens the chat, the gateway remembers the newest text bubble on screen. After Send, before leaving the chat, it reads the customer text bubbles below that bubble (text and time label), above and below the bubble it just sent, and records those not yet recorded for that chat, so messages that arrived while the chat was open, even while our text was being typed, are not lost. Equal bubbles in the same minute count as separate messages. When the remembered bubble is no longer on screen, or the chat showed none, only the bubbles below ours are read. Reactions, deletions, edits and media sends skip this, because they can leave the chat scrolled up, where older bubbles sit below ours.
- PGW-26: Every 2 minutes while the phone is idle, the gateway opens the WhatsApp chat list with its task cleared, so WhatsApp never resumes the last open chat, closes the backup prompt if it is shown, and goes back to the home screen after one screenshot. For each visible chat whose last message is ours, it records the chat name, the preview text and the tick. The chat list shows the tick only as an icon, so it is read from the screenshot: mostly blue is read, otherwise a wide icon is delivered and a narrow one sent; the colour and width figures are kept with the record. A record is written only when the tick of that chat and preview changes, so a new message of ours that reaches the same tick as the previous one is still reported.
- PGW-27: In phase 1 all records go only to `state/incoming/<date>.jsonl` and the media folder, both kept 14 days like PGW-20. Nothing is sent to the backend, no chat is opened for capture alone, and nothing is marked as read.
- PGW-28 (RFC-012 phase 2): When `BACKEND_EVENTS_URL` is set, every recorded message and tick of a physical phone is also queued (PGW-40) and posted in order to the backend with the bearer `GATEWAY_TOKEN` as soon as it is queued, and retried until the backend answers 2xx. A message whose sender is shown by number carries that number as `phone`. The event ID is the record key, so a retry is never stored twice. A media message is sent only after its file is matched or reported missing (PGW-24). A voice note goes out as `.oga` with `audio/ogg; codecs=opus`, the form Whapi uses, because iOS does not play the same file named `.opus` as plain `audio/ogg`. A notification text that is only WhatsApp's media placeholder ("Sent a photo", "Photo", "Video", "Voice message (0:05)" and the like) is not sent as a caption.
- PGW-29: A matched media file is served at `GET /v1/incoming-media/<name>?sig=<signature>`, where the signature is an HMAC of the name with `GATEWAY_TOKEN`; the event carries that URL, its MIME type and file name. Files are deleted with the records (PGW-27).
- PGW-30: A tick event needs the customer phone. A chat name that is a phone number gives it directly; any other name is resolved from the chat header the gateway read when it last opened a chat for that phone (`check_recipient`). A tick for a name with no known phone is only recorded. A message captured from an open chat (PGW-25) carries `<to>@s.whatsapp.net` and the capture time, because it arrived while the chat was open and its label shows only the minute.
- PGW-31: After a text send succeeds on a physical phone, an `outgoing` event with the request's message ID, recipient and text is queued like PGW-28, so the backend can show texts the warmer sent through the phone.
- PGW-32: A voice note or audio file is converted to M4A (AAC) with a unique title, placed in the phone's music folder and indexed, and sent through the chat opened for `to` (PGW-9): attach → Document → Browse audio, then that title only. If WhatsApp asks for access to audio files, the gateway allows it. The picker is opened from the chat `check_recipient` verified and sends to it; its confirmation dialog shows the recipient only as an image, so the gateway checks that the dialog sits on WhatsApp's audio picker and otherwise cancels and fails as not retryable. The tap on Send in that dialog is recorded like Send (PGW-3), and the newest bubble of ours must then be an audio message, otherwise the outcome is `unknown`. WhatsApp shows it with a headphones icon and a player, not as a recorded voice note; a real voice note needs the microphone, which a phone without root cannot be fed. The file is deleted from the phone afterwards (PGW-11).
- PGW-33: For each physical phone the offline check of PGW-18 is also reported to the backend as a `state` event: online at the first answer and after a recovery, offline after the same two misses that raise the alert.
- PGW-34: When the registry gives no `whatsappPackage`, the gateway reads the installed packages on the first connection: only WhatsApp Business installed selects `com.whatsapp.w4b`, otherwise `com.whatsapp`. With both installed the registry has to name the app.
- PGW-35: The first time a sender shown only by number writes from a chat, the gateway opens that chat, then its contact info, reads the title and the "~ name" line the person set in WhatsApp, and goes back to the home screen. This marks the chat as read. A WhatsApp Business account shows its business name in place of the contact title, and that name is used. While the chat is open WhatsApp raises no notification for it, so before leaving the gateway reads the customer text bubbles below the one it saw on opening and records them like PGW-25; when that bubble is no longer on screen nothing is taken. The name is sent as a `profile` event and the chat is not read again. WhatsApp blocks screenshots of the contact info screen, so no profile photo is taken.
- PGW-11: After each operation WhatsApp is sent to the background so new incoming messages are not marked as read by an open chat. Media copied to the phone is deleted afterwards.
- PGW-36: For the ADB serials in `FAST_UI_SERIALS`, the screen is read through a resident uiautomator2 server (`u2.jar` from `FAST_UI_JAR`, pushed to the phone and started on demand, reached through an ADB forward) instead of a new `uiautomator dump` each time: well under a second instead of 3-4 seconds. When the server does not answer, it is stopped, because Android allows one UI reader at a time, and the plain dump is used for a minute before the server is tried again.
- PGW-37: On the phones in `FAST_UI_SERIALS` (on trial), after a text send the chat stays open for 8 seconds. A text to the same recipient in that time is typed into it when the chat with the same header is still in front, without opening it again; its open-chat capture (PGW-25) goes on from the newest bubble the last look saw. Any other operation, or the end of the 8 seconds, first reads the customer bubbles that came in (PGW-25) and then goes to the home screen. The 5-second notification poll leaves the chat open and skips profile reads and the chat-list tick scan while it is.
- PGW-38: Before a photo or video is shared, the gateway grants the WhatsApp app photo and video access (`READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO`, `READ_MEDIA_VISUAL_USER_SELECTED`), once per phone and app in each gateway run. Without it WhatsApp ignores the chat named in the share and opens its own "Send to…" picker, so no media composer appears (seen with WhatsApp Business 2.26.43 on the physical phones, 2026-11-05).
- PGW-39: WhatsApp Business opens a shared video in its contact picker with the chat already selected, not in the "Share with" dialog. The gateway taps the picker's next button only for a video, only when exactly one recipient chip is selected and its digits are exactly `to`; that opens the media composer, where View Once, the recipient check and Send follow as usual. Any other picker state fails before Send.
- PGW-40: The phone event queue is the SQLite table `events` in `state/incoming/events.sqlite` (WAL, full sync). An event is committed when it is recorded and leaves the queue only by its own ID once the backend answered 2xx for the batch that carried it, so an event recorded while a batch is in flight, or one of another phone, is never removed. Batches hold up to 50 events of one phone in recorded order, the phone whose oldest waiting event is oldest going first. A network error or any status other than 400 and 422 is the backend being unavailable: the phone's first event waits 1 s, then twice as long each time up to 5 minutes, and is never set aside. A 400 or 422 splits the batch: its first event goes alone, and an event refused three times (its batch counts once) is marked `parked` with the error, so it cannot hold back that phone; parked events stay in the table until requeued. Sent events are kept 14 days. On first start the earlier `outbox.json` is imported in order and renamed `outbox.json.imported`.
- PGW-42: For each physical phone that captures incoming messages, the gateway keeps the phone's system log open over ADB, filtered on the phone to the `NotificationManager` tag (`logcat -T 1 NotificationManager:I *:S`). A line saying that WhatsApp or WhatsApp Business posted a notification (`com.whatsapp[.w4b]: notify(`) starts a capture round for that phone at once; one that arrives while a round runs starts another right after it. The stream is restarted 5 s after it ends (an ADB reconnect, a phone restart). The poll of PGW-23 stays every 5 s as the fallback, so a stream that stops without ending only delays a message.
- PGW-43: A customer message that reaches a chat in the moment the gateway leaves it gets no notification and is shown read, so no unread badge marks it either. 3 s after the gateway leaves a chat it sent to (after the last part when several follow each other), it reads the notifications, then the chat list once. When that chat's row shows a last message from the customer (no tick icon) whose text, or its start for a long one, was not recorded in the last 3 minutes, the chat is opened and the customer text bubbles below the one last seen there are recorded as in PGW-25. A customer text recorded in the last 3 minutes by one way (notification or chat) is not recorded again by the other.

## Validation

`npm run build` type-checks the service. `npm test` covers the UI tree parser, selector matching, recovery tap restrictions and script proposal validation. Device behavior has no hermetic coverage. It is checked on a test number by sending text, a photo and a View Once photo, and by changing a selector to force recovery and a fixer proposal.
